## 2. 为什么走 TDM（背景，30 秒读懂）

HSTU fwd 在 gfx1250 上目前走 T1 照抄 gfx95 的 **trload** 路径
（`hstu_attention_batched_forward_dispatch.hpp:43`，`#ifdef BUILD_HSTU_FOR_GFX95` 被扩成
`|| defined(BUILD_HSTU_FOR_GFX125)`）。trload 要做 transpose，transpose 对 tile distribution
encoding 有校验（`load_tile_transpose.hpp:677` 的 `ValidationTraits::value`），softmax 路径的
`WarpTile_32x32x16` 过不了 —— 这就是上一份 HANDOFF §3.1 那 96 个编不过的实例。

**PR #7755 表明 AMD 给 gfx1250 的答案不是 trload，而是 TDM**：走 `load_tile_tdm` 硬件 box-major
DMA 直接 global→LDS（不经 VGPR），配 plain row-major LDS，**整条 XOR swizzle 链拆掉**，用
`s_wait_tensorcnt_barrier`（独立的 tensorcnt 计数器）同步。TDM 路径不做 transpose，那个断言天然不存在。

**上一轮的 WMMA 替换正是这条路的前置条件**（96 实例全部编译、221184 `v_wmma` / 0 `v_mfma`、
91/96 真机对拍通过）—— 详见 `project_hstu-tdm-pipeline/HSTU_NOSOFTMAX_96_REPORT_2026-08-19.html`。

## 7. Step 2–7 计划（设计已定）

完整计划见 `project_hstu-tdm-pipeline/TASK_TEMPLATE.md`，以及 plan 文件
`/data/.claude/plans/vast-cooking-lerdorf.md`（⚠️ 在易失层，内容已并入 TASK_TEMPLATE）。

### 7.1 核心洞察：难点不是 XOR，是 dram tile distribution

拆 XOR 是**纯机械**的（删模板参数、删 `if constexpr(Xor)` 分支、提升 `else`）。真正的核心是：

**TDM 的 `box_dim` 是从 dram window 的 tile distribution 反推出来的** ——
`tile_window.hpp:893-898`：`box_dim = ys_to_d.get_lengths().reverse()`。
原来的 5D lane-scatter dist 推出来的 box 是散的，硬件 box 写进 LDS 后读端读到垃圾。
**这就是 PR 里 V 那个 1.6% 字节吻合率的根因。**

必须换成 **trivial tile-major**：每个 **wave** 拿一整块连续 `(MN/warpNum) × K` 矩形，
配 `IsWarpLevelParallelOnly=true`（TDM 是 wave 级指令）。模板源头是 GEMM TDM policy
（`gemm_pipeline_ag_bg_cr_comp_tdm_default_policy.hpp:83-91 / 150-158`）。

### 7.2 分步（每步只变一个变量，每步都回 63/64 基线验证）

| Step | 内容 | 验证 |
|---|---|---|
| **2** | 建 HSTU TDM pipeline 骨架 + **把 K/V 的 LDS 布局打平**（仍用老 loader） | 只变 LDS 布局 → 63/64 |
| **3** | K/V 的 dram dist 换 trivial tile-major（仍用老 loader） | 只变 dist → 63/64 |
| **4** | kernel 侧 **K/V** dram view 改 affine（跳过 `unmerge→xor→merge_v3`） | 63/64 |
| **5** | 换 `load_tile_tdm` + `s_wait_tensorcnt_barrier` | 只剩 TDM 指令一个变量；**字节级对拍** |
| **6** | 派发三态 enum + 收窄（`static_assert` 挡 dropout / MaxK≠128） | 63/64 + 48 个 dropout 实例回落 trload |
| **7** | prefill（MTile=128）+ P relayout；**补回 §3.5 的 bm0=128 tile 条目** | MTile 64/128 分别对拍 |

**方法论（照搬上游，别省）**：先用老 loader 把新 pipeline 跑通拿到功能正确基线，
再逐个操作数换新硬件。上游明知此阶段性能 −21%~−32% 也坚持先拿基线 —— 这样每步出问题能二分定位，
V 那个 1.6% 的坑就是这么抓出来的。

### 7.3 已定决策（用户拍板）

1. **只 K/V 走 TDM，Q 完全不动。** HSTU 的 Q 是 load-once 直接进寄存器、**没有 Q 的 LDS descriptor**
   （与 FMHA 的 Q-through-LDS 是结构性差异）。TDM 收益集中在 K/V 的循环加载。
2. **做 Step 1 的 FMHA 真机验证**（已完成）。
3. **范围收窄到 batch + jagged**，group mode 放下。

### 7.4 Step 2 的具体改动（比原估计小得多）

**`MakeKLdsBlockDescriptor` 里已经有一个 plain row-major 分支** ——
`hstu_attention_fwd_pipeline_policy.hpp:216` 的 `!IsPerfectHeaddimSize(kKPerBlock)`
（原本为 hdim 96/160 写的"最简布局"）：naive 3D → merge 2D，**无 xor**，
且 size（`kNPerBlock*kKPerBlock`）与 xor 分支（`:166`）**完全相同**。

所以：
1. `MakeKLdsBlockDescriptor` 加 `bool kPlainLds = false`，条件改成
   `!IsPerfectHeaddimSize(kKPerBlock) || kPlainLds`
2. `MakeVLdsBlockDescriptor` 加同样参数，在 trload 分支（`:453-494`）里给一个去掉
   `make_xor_transform` 的 plain 版（naive 3D → merge 2D，形状仍是 `[NumBuf*kK1, kN1]`）
3. **`GetSmemSize` / `GetSingleSmemElementSpaceSize` 一概不用改**（size 相同）

## 9. 踩过的坑（照着避）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `ninja -j $(nproc)`（255）编 CK 实例 | OOM killer 杀 clang，报 `unable to execute command: Killed` + `exit code -2`，**长得像编译错误** | 用 `-j 24`。看到这个报错先查 `free -g`，别去查代码 |
| `pkill -f "ninja -j"` / `pgrep -f "..."` | **匹配到自己的 bash 命令行**，导致自杀（exit 144）或误报 RUNNING | 用 `pkill -x ninja` / `pgrep -x` |
| `timeout N <cmd>` 的子进程 | TaskStop 后**不会被杀**（脱离任务组），继续占 GPU | 手工 `kill -9` 子进程 PID |
| 后台脚本起了两个实例 | 两个 HSTU 进程并发抢 GPU，疑似触发 wedge | 启动后 `pgrep -af` 确认只有一个 |
| batched 模式传多值 `-seqlens` | 32 个 case 全 `rc=134`，`'1 == seq_lengths_q.size()'` | batched **只能单值**（`-seqlens=128`）；jagged 才能多值 |
| 并行 `llvm-objdump` 写同一 stdout | 输出交错撕裂成碎片，指令计数偏差 | 每进程写各自文件再汇总 |
| 「输出为空 = 没有失败」 | 实际是**卡住了**，第一个 case 跑了 3 分钟 | 空输出必须查进程状态（`ps -eo etime`），不能想当然 |
| `git cherry-pick -n` | 会 stage 改动，等同 `git add`，**违反红线** | `git apply --exclude=...`，全程不进 index |
| `rc=254` 的两义性 | 既可能是数值不匹配，也可能是 launcher 主动拒绝 | 靠 stderr 首行区分；**没有 PASS 字符串可 grep**，只能看 exit code + dump |
