Step 0 回归 0 条结果

1为什么是 TDM 而不是 trload

这个方向不是新选的，而是承接上一轮 WMMA 替换的自然下一步。

HSTU fwd 在 gfx1250 上目前走的是 T1 照抄 gfx95 的 trload 路径 （hstu_attention_batched_forward_dispatch.hpp:43 把 #ifdef BUILD_HSTU_FOR_GFX95 扩成了 || defined(BUILD_HSTU_FOR_GFX125)）。trload 要做 transpose，而 transpose 对 tile distribution encoding 有校验（load_tile_transpose.hpp:677 的 ValidationTraits::value）， softmax 路径的 WarpTile_32x32x16 过不了 —— 这就是 HANDOFF §3.1 那 96 个编不过的实例。

PR #7755 表明 AMD 给 gfx1250 的答案不是 trload，而是 TDM：Q/K/V 走 load_tile_tdm 硬件 box-major DMA 直接 global→LDS（不经 VGPR），配 plain row-major LDS，整条 XOR swizzle 链拆掉， 用 s_wait_tensorcnt_barrier（独立的 tensorcnt 计数器）而非 block_sync_lds_direct_load 同步。 TDM 路径根本不做 transpose，那个断言天然不存在。

1.1 一个必须先厘清的事实

PR #7755 的 squash commit 是 a2ebc0513（2026-07-21，12 文件 / +2722）。它确实在本仓库里， 但只在 remotes/upstream/develop 上：

git merge-base --is-ancestor a2ebc0513 HEAD  → 否
git branch -a --contains a2ebc0513           → remotes/upstream/develop   (仅此一个)

即：fetch 下来了、git show 读得到，但 hstu_attention_fwd_450 这条分支上没有它， 工作区也确实没有那两个 tdm 文件。所以它是可直接本地引用的蓝本，不是已生效的代码。 我们的分支落后 upstream/develop 74 个 commit。

1.2 核心洞察：难点不是 XOR，是 dram tile distribution

拆 XOR 是纯机械的（删模板参数、删 if constexpr(Xor) 分支、提升 else）。真正的核心是：

TDM 的 box_dim 是从 dram window 的 tile distribution 反推出来的 —— tile_window.hpp:893-898：box_dim = ys_to_d.get_lengths().reverse()。 原来的 5D lane-scatter dist 推出来的 box 是散的，硬件 box 写进 LDS 后读端读到垃圾。 这就是 PR 里 V 那个 1.6% 字节吻合率的根因。

5Step 2 的设计发现（改动比预想小）

MakeKLdsBlockDescriptor 里已经有一个 plain row-major 分支 —— hstu_attention_fwd_pipeline_policy.hpp:216 的 !IsPerfectHeaddimSize(kKPerBlock) （原本为 hdim 96/160 写的"最简布局"）：naive 3D → merge 2D，无 xor， 且 size (kNPerBlock*kKPerBlock) 与 xor 分支（:166）完全相同。

这意味着 Step 2 的 policy 改动是：

  1. MakeKLdsBlockDescriptor 加 bool kPlainLds = false，条件改成 !IsPerfectHeaddimSize(kKPerBlock) || kPlainLds
  2. MakeVLdsBlockDescriptor 加同样参数，在 trload 分支里给一个去掉 make_xor_transform 的 plain 版（naive 3D → merge 2D，形状仍是 [NumBuf*kK1, kN1]）
  3. GetSmemSize / GetSingleSmemElementSpaceSize 等 一概不用改（size 相同）

5.1 其它已摸清的结构事实

发现影响
HSTU 的 trload 与非 trload pipeline 只差 10 处，其余逐字相同TDM 版可按"复制 + 改 policy 布尔参数 + 改 V 路径"做
HSTU 的 Q 是 load-once 直接进寄存器，没有 Q 的 LDS descriptor（FMHA 的 Q 走 LDS）已定决策：只 K/V 走 TDM，Q 完全不动
use_trload_pipeline 有 9 个消费点（6 fwd + 3 bwd），6 个 fwd 的选择代码块逐字复制开关需升级成三态 enum，否则 trload && tdm 组合爆炸
jagged/group 在 pipeline 层完全不感知（kIsJagged 在函数体内 0 次引用），全在 kernel 层TDM pipeline 不用管变长逻辑
HSTU 无 softmax → 无 running max/sum、无 sink省掉 PR 的 commit 15/16
core 层（load_tile.hpp / amd_tdm_descriptor.hpp / buffer_view.hpp）与 upstream 零差异TDM 底层设施齐备，无需同步 74 commit
tile 形状 <M=128,N0=32,N0Sub=32,N1=128,K1=32>，warpNum=4满足 TDM 新增的 kM0%warpNum==0、kN0%warpNum==0；contiguous 维 256B ≥ 128B 满足最佳吞吐

5.2 高危项

CK_TILE_ENABLE_TDM_FEATURE 只在 __gfx125__ 下为 1（config.hpp:221-225）， 否则 amd_tdm_load / s_wait_tensorcnt 编译成空且不报错 —— 直接静默产生错误结果。 必须靠 Step 6 的门控 + static_assert 挡死。

6.2 触发原因 —— 推断，未证实

我的回归脚本被启动成了两个并发实例（PID 86644/86645 同时跑 batched 和 jagged 的不同 case）， 这是我的操作失误。但两个进程共享 GPU 本不该导致 MES ring 溢出，所以不能断定这就是根因。 也不排除是这张卡 / 驱动版本的已知不稳定性 —— 上次 wedge 同样以 MES 报错起头。
